## 1. Put the current code on GitHub

The configured repository is `https://github.com/denusha1/WayToHome`. Run from the project root:

```bash
git status
```

Review changed files. Use your editor's Source Control to stage and commit the application, scripts, docs, tests and deployment configuration, then push to your GitHub repository. Do not stage populated `.env` files. Environment **example** files contain blank/sample values and belong in the repository. Hosting imports the code pushed to GitHub, not unsaved local edits.

## 2. Create the accounts (your step)

Open and sign into Vercel, Railway, Supabase and PayHere Sandbox. Use your own account email and complete any verification. Connect GitHub to Vercel/Railway and grant access to this repository. Choose/approve any required hosting plan yourself.

Record project names and public URLs in your notes. Those can be shared with me. Put secret keys only in your local ignored environment files or the provider's Variables/Environment Variables settings; do not paste them into chat.

## 3. Prepare Supabase authentication

Create a Supabase project. From its connection/API settings obtain the project URL and the legacy public `anon` key used by this application. Do not substitute a service-role key. Put the same URL/public key in both frontend and backend variables below.

In Auth settings, enable email login and configure the email sender. Enable phone authentication and configure a supported SMS provider for OTP. For Google login, create OAuth credentials in Google Cloud, copy the callback URL displayed by Supabase into Google's authorized redirect URIs, and enter Google's client ID/secret in the Supabase Google provider settings. Those Google secrets stay in Supabase, not frontend code. See the [official Google setup guide](https://supabase.com/docs/guides/auth/social-login/auth-google).

When the final frontend domain is known, set it as the Supabase Site URL. Allow `/login` on that exact HTTPS domain, including the `next` query variants generated by the app. `/login?next=%2Fbookings` and `/login?next=%2Fadmin` are common examples. Verify a login actually returns to the intended page. See [redirect configuration](https://supabase.com/docs/guides/auth/redirect-urls).

Create a traveller account and an admin account through the signup flow after deployment. Copy the admin user's UUID from Supabase and place it in backend `ADMIN_USER_IDS`. Never grant admin using a browser/profile field.

## 4. Create the Railway backend and database

Create a Railway project. Add PostgreSQL, then add a service from this GitHub repository. The API service must build using the repository root as context: `apps/api/Dockerfile` and `railway.toml` are already included. Do not make `apps/api` the Docker build context; the Dockerfile needs the workspace manifests and lockfile from the root.

Generate the API service's public HTTPS domain and note it. In its Variables settings add the values listed in `apps/api/.env.production.example`:

| Variable                                | Value/source                                                 |
| --------------------------------------- | ------------------------------------------------------------ |
| `NODE_ENV`                              | `production`                                                 |
| `DEMO_MODE`                             | `false`                                                      |
| `DATABASE_URL`                          | Reference the Railway PostgreSQL service's connection string |
| `WEB_URL`                               | Final Vercel HTTPS origin, without a trailing slash          |
| `API_PUBLIC_URL`                        | This Railway API HTTPS origin, without a trailing slash      |
| `SUPABASE_URL`                          | Supabase project URL                                         |
| `SUPABASE_ANON_KEY`                     | Matching public legacy anon key                              |
| `ADMIN_USER_IDS`                        | Supabase admin user UUID; add after creating that user       |
| `TICKET_SECRET`                         | Private random secret generated locally; keep stable         |
| `PAYHERE_SANDBOX`                       | `true`                                                       |
| `PAYHERE_MERCHANT_ID`                   | PayHere sandbox merchant ID                                  |
| `PAYHERE_MERCHANT_SECRET`               | Sandbox merchant secret approved for the website domain      |
| `PAYHERE_APP_ID` / `PAYHERE_APP_SECRET` | Separate sandbox Merchant API credentials for refunds        |
| `TRUST_PROXY_HOPS`                      | Verified number of reverse proxies; do not guess             |

Generate the ticket secret in your terminal with `openssl rand -hex 32` and copy it directly into the backend variable. The host supplies the runtime port. The release configuration runs migrations and checks `/api/health/ready`. A first deployment without the required credentials is expected to fail; fill the remaining values and redeploy. Do not enable demo mode to bypass that failure.

The source configuration and release command are documented in [Railway's reference](https://docs.railway.com/config-as-code/reference).

## 5. Create the Vercel frontend

Import the GitHub repository as a new Vercel project. Select Next.js and set Root Directory to `apps/web`. Allow access to files outside this root so the workspace can use its root lockfile. Keep the default Next.js build/output settings. See [Vercel's monorepo guide](https://vercel.com/docs/monorepos).

Add these frontend variables:

```text
NEXT_PUBLIC_API_URL = Railway HTTPS origin
NEXT_PUBLIC_SUPABASE_URL = Supabase project URL
NEXT_PUBLIC_SUPABASE_ANON_KEY = matching public anon key
```

Deploy and note the final frontend URL. Update `WEB_URL` on Railway, Supabase's allowed callbacks and PayHere's allowed website domain to match it. Frontend environment changes require a new build/deployment. If changing domains later, update all these places together.

## 6. Configure PayHere sandbox

In PayHere sandbox, obtain the merchant ID and add the website domain in its integration settings to obtain the domain-specific merchant secret. Put both in Railway. For refunds create the separate Merchant API credentials and put the app ID/secret in Railway too. The app generates the checkout return/cancel URLs and the notification URL from `WEB_URL` and `API_PUBLIC_URL`.

The notification endpoint is `https://YOUR-API-DOMAIN/api/payments/notify`. It must be publicly reachable by PayHere. Use the provider's documented sandbox test cards, never real card details for this walkthrough. Provider setup/approval and actual transaction evidence are required before calling the integration verified. References: [checkout](https://support.payhere.lk/api-&-mobile-sdk/checkout-api), [refund](https://support.payhere.lk/api-&-mobile-sdk/refund-api), [sandbox testing](https://support.payhere.lk/sandbox-&-testing).

## 7. Validate configuration and the deployed flows

Optionally copy the templates into the ignored local filenames used by the checker, fill them privately, and run `npm run deploy:check`. This switches those local configurations away from the demo; keep a private backup of any existing config first. The checker never prints secret values. It validates configuration, not deployment or provider delivery.

On the public deployment, perform these checks:

1. API `/api/health/ready` returns 200. `/api/health` reports `demo: false`.
2. Sign up a traveller; verify email login, phone OTP and Google login individually. Sign out and confirm My Bookings needs login again.
3. A traveller cannot open Admin. The configured admin can add a clearly labelled test bus, route and future departure.
4. Book seats using a PayHere sandbox success payment. Wait for verified backend confirmation; open the QR ticket.
5. Test failed and cancelled checkout. Neither must produce a confirmed ticket from a browser redirect alone.
6. Request cancellation for a confirmed sandbox booking. Approve the full refund in Admin, then verify its reference in PayHere, booking status and invalidated ticket.
7. Save non-secret evidence: deployed URLs, date, scenario, result, sandbox booking/reference IDs. Never include credentials, OTPs or real passenger data in screenshots.

See `RELEASE.md` for duplicate/late-payment and ambiguous-refund handling. If anything fails, send the public URL, step and redacted error message. I can inspect/fix the code and continue the technical work. Receiving OTPs, choosing provider account settings and granting account access still need your participation.
